# Code Implementation

Use the sections relevant to the current decision. They support creation, refinement, and review without prescribing a coding workflow. Apply [Code rules](rules.md); review findings do not authorize edits.

## Readability

**Names and conventions.** Choose terms used by the project and its domain. Make important distinctions visible, such as a duration's unit or a value's validated state. Use ordinary language and established language idioms. Short local names can be clear; public names may need more context. Preserve public compatibility and avoid renaming for taste. Check whether the caller can understand the operation without inspecting its implementation.

**Control flow and structure.** Keep related work together and make conditions, state changes, and side effects easy to follow. Flatten nesting when it improves the main path, but preserve cleanup and ordering. Extract a function when its name explains a meaningful operation or it isolates a responsibility. A helper used once can be useful; a wrapper that only forwards arguments may add navigation without explaining anything. Prefer explicit branches over compressed expressions when outcomes differ materially.

**Comments and documentation.** Explain information the code cannot show clearly: a constraint, decision, invariant, workaround, or external contract. Describe complex algorithms when needed. API documentation may explain inputs, outputs, failures, and side effects even when the implementation is short. For example, “Returns None when no matching record exists” can define essential behavior. Keep it if callers need that distinction. Update misleading comments when behavior changes; do not replace them with line-by-line narration.

## Simplicity

**Reuse and responsibility.** Locate the existing owner and a comparable implementation before adding behavior. Reuse only when behavior fits: a direct database call is not equivalent to a service that also enforces access or filtering. Share logic that represents the same policy and should change together. Similar-looking code with different responsibilities can remain separate. Fix a caller that violates a valid contract; repair shared code when its behavior or contract conflicts with requirements. Check the cause rather than adding a local workaround or copying an existing defect. Preserve documented extension or platform boundaries; a single implementation does not make an interface unnecessary.

**Scope and confirmation.** Use project evidence to choose routine implementation details within the user's scope. When not already authorized, ask before a redesign, breaking contract change, dependency replacement, or data migration. Ask about an unresolved product decision when its consequences materially affect the work and project evidence offers no defensible default. Inspect enough to present a concrete reason, affected behavior, and a smaller alternative when available. Continue independent authorized work while awaiting the decision; wait before making dependent changes. Do not ask again for approved work. If clarification is unavailable, preserve the current contract and report the limitation. An authorized API rename may require many caller updates; a local bug fix does not authorize replacing the storage layer.

**Abstraction and configuration.** Choose the smallest design that meets the actual requirements and remains understandable. A direct function may suffice where a factory and registry add no present capability. Introduce a shared abstraction when it clarifies ownership, prevents inconsistent policy, or supports required variation. An option needs a real consumer or operating requirement. Inline a constant when its name adds no meaning, but retain names that communicate units, domain concepts, or coordinated values. Judge the information gained, not the number of uses.

**Dependencies.** Compare existing, native, and external solutions by behavior, compatibility, maintenance, security, and implementation cost. A maintained dependency can be simpler than custom protocol or parsing code. Before recommending or installing a new package, verify its source and identity; existence or popularity alone does not establish safety. For added or changed dependencies, check relevant security advisories and supported releases with available tools; a clean scan is not a safety guarantee. Update affected manifests and lockfiles through project conventions without unrelated upgrades. Identify material checks that could not be performed.

**Generated files.** Update the owning source and regenerate affected artifacts through the project's existing process when required. Do not hand-edit output contrary to project policy or regenerate unrelated artifacts. If regeneration is unavailable, identify the affected deliverable and what remains incomplete or unverified.

## Correctness

**API and version compatibility.** Identify supported language, runtime, dependency, and platform versions from manifests, lockfiles, toolchain configuration, and deployment or CI requirements. A local runtime or a manifest's version range alone may not establish every supported target. For a new project without declared targets, select maintained stable versions that meet its constraints and state consequential choices.

Use current official documentation for the target version, including migration or deprecation notes when relevant. Check imports, signatures, return values, failure behavior, and execution context; examples from different major versions, browser/server environments, or sync/async APIs are not interchangeable. Prefer a supported replacement for new code when it fits. Keep required compatibility paths and distinguish deprecated APIs from merely older syntax. Do not upgrade the stack or migrate working code solely to match the latest documentation. Verify relevant calls in the target environment when possible; retrieved documentation or a plausible API name does not prove execution.

**Required behavior.** Identify inputs, outputs, side effects, and intended changes from requirements and actual callers. When plausible interpretations produce different outcomes, resolve the difference from project evidence or a focused question; do not silently choose a product rule. A small input/output example can clarify the decision without a formal specification. For deduplication, establish whether order must be preserved and which occurrence to retain. Preserve observable behavior in a refactor; for a bug fix, distinguish defective behavior from behavior users still require.

**Integration.** For behavior intended for the product, confirm that the actual route, handler, worker, public API, or other entry point reaches it. A function exercised only by its own test does not establish feature delivery. Account for dynamic registration, framework hooks, and documented library entry points before declaring code unused. Follow affected uses far enough to catch broken exports, configuration, fixtures, or documentation. Check that mocks do not remove the behavior being evaluated. Formatting improvements or a smaller diff cannot establish completeness.

**Result states.** Distinguish empty, absent, pending, failed, and legitimately degraded results when callers need to react differently. A failed stock lookup is not a stock count of zero. A cached result may be valid if its source and freshness meet the contract and callers can recognize relevant limitations. Represent these distinctions through the project's existing data and error conventions; use nulls, booleans, or defaults only when their meaning is unambiguous.

**Failures and validation.** Validate where data crosses a trust boundary or a required invariant is uncertain. Avoid repeating checks without an additional responsibility. Catch failures when the code can recover, translate them into its documented contract, or add useful context. Otherwise propagate them appropriately. A fallback must still meet the documented contract rather than hide failed work. Preserve failure causes without exposing secrets or sensitive data.

**State and operational risks.** For asynchronous or stateful work, consider ordering, partial completion, cancellation, cleanup, and repeated execution where relevant. Wait on the actual result or state instead of adding an arbitrary sleep to make a race disappear. Retry only suitable transient failures; bound attempts and avoid duplicating effects when the outcome is unknown. For user or tenant data, preserve authorization and data scope. Keep untrusted data separate from executable query or command text, and do not embed real secrets in source or fallback values. For large inputs, consider memory use, query count, and bounded concurrency. Address the risks affected by the change rather than imposing a full audit on every edit.

**Checks and evidence.** Choose checks that could expose the relevant mistake, using existing project tools where practical. Useful evidence may come from caller inspection, type checks, targeted tests, or execution of the affected path. Check behavior and failure conditions when they matter; an import check, nonempty diff, or compilation result proves less. Tests should assert the required outcome rather than mirror implementation details. State what actually ran and what remains unverified. Review findings should identify the location, concrete impact, and supporting evidence; separate defects from preferences. Stop when the requested scope is met without unresolved material issues.

Further reading: [Google's code review criteria](https://google.github.io/eng-practices/review/reviewer/looking-for.html) for implementation quality, and [OWASP Secure Coding with AI](https://cheatsheetseries.owasp.org/cheatsheets/Secure_Coding_with_AI_Cheat_Sheet.html) for dependency and security risks. Their organizational procedures, tooling choices, and fixed thresholds are not requirements here.
